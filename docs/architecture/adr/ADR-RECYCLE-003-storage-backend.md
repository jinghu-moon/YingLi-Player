# ADR-RECYCLE-003：回收站存储后端——R1 系统回收站为主、R2 应用副本为受控降级

## 1. 背景

### 1.1 冲突陈述

项目内存在一处**直接的冲突**，必须裁决：

- `docs/06-feature-roadmap.md:264`：「默认先进入统一的影里回收站页面；**底层优先使用 MediaStore 系统回收站**，能力不足时使用受控降级实现；永久删除为明确的二次确认」→ 倾向 **R1 优先**。
- 参考资料 `ADR-XXX：采用应用自主管理的 30 天视频回收站.md`（状态「待基线审查」，2026-10-09）：「Android 系统回收站的到期时间由系统掌控，不能用它直接兑现应用自定义的严格 30 天期限。因此，本文采用应用自主管理的回收站记录与副本」→ 倾向 **R2**。
- 参考资料文件 8 §1.1：「如果产品要求『回收站内每个私有副本的单项删除必须出现 Android 系统媒体授权弹窗』，则与应用专属副本存储方案不兼容」。
- **当前代码是 R3**（`DefaultLibraryMutationRepository.trash()` 用 `renameTo(".Trash/YingLi/<name>")`），且对 `content://` 直接失败。

### 1.2 第一性原理

**「可恢复的删除」要求字节仍然存在。** 由此推出，只有四种可能的存储后端，且**互斥**：

| 方案 | 机制 | 额外空间 | 能否保证「严格 30 天可恢复」 | 适用来源 | 卸载后 | 系统授权弹窗 |
| --- | --- | --- | --- | --- | --- | --- |
| **R1 系统回收站** | `MediaStore.createTrashRequest()`（他应用媒体）或直接置 `IS_TRASHED = 1`（本应用媒体）；期限读 `MediaStore.DATE_EXPIRES` | **0** | **否**（`DATE_EXPIRES` 只读，系统空闲时物理删除） | 仅 MediaStore 共享媒体 | 文件与系统状态仍在，卸载后**其他应用仍能看到系统回收站内容** | 需要（仅他应用媒体） |
| **R2 应用专属副本** | 复制到 `filesDir/recycle-bin/items/<uuid>`，验证副本后请求删除源 | **≈ 原文件大小**（移入阶段峰值可达 2×） | **是** | 全部（含 SAF 树） | **副本随卸载删除** | 删除源时需要（若源在共享媒体库） |
| **R3 同卷隐藏目录移动** | `renameTo(".Trash/YingLi/<name>")`（**当前实现**） | 0 | **是**（只要 rename 成功） | **仅 `file://`** | 保留 | 无 |
| **R4 阻止并解释** | 不执行，只说明原因 | 0 | — | 全部 | — | 无 |

### 1.3 两个决定性的代价

- **空间**：在手机存储是最稀缺资源的场景下，「为了能回收一份 2 GB 的视频而先复制一份 2 GB」是产品上难以接受的。
- **期限**：`MediaStore.DATE_EXPIRES` 是**只读**字段；系统默认保留约 30 天，但**过期文件通常到设备下一次空闲才删除**。因此 R1 的 30 天**由系统掌控，应用不能延长或缩短**。
- **R3 根本不成立**：应用对其他应用创建的共享媒体**没有路径访问权**，`renameTo` 不成立；它「成功」时（`file://`）也只是把文件搬进一个既不受系统保护、也不受应用期限管理的隐藏目录，并且会让原 URI 失效、需要重新扫描。

## 2. 决策

**R1 为主后端，R2 为受控降级，R3 删除，R4 兜底（对应 D2-a）。**

1. **R1 是默认路径**：它是唯一**零空间代价**的可恢复删除——字节本来就在，只是被系统标记。
2. **R3 必须删除**。这是本项目当前最大的正确性缺陷。
3. **R2 只在 R1 不可用时启用**，且**必须先通过 P0-B 验证**（SAF 树没有系统回收站；部分来源没有删除权）。
4. **R4 是默认的失败处理**：不支持或无法可靠操作的文件**必须阻止操作并解释原因**，不能静默永久删除。
5. **接受「两类条目、两种期限语义」**，UI 按后端分别显示剩余期限与说明。

### 2.1 必须原样写进 UI 的期限语义

| 后端 | 期限语义 | 必须披露 |
| --- | --- | --- |
| R1 | 「由系统管理，通常约 30 天；到期后系统在设备空闲时删除。**应用不能延长或缩短这个期限**」 | 恢复资格取决于系统是否已删除；`DATE_EXPIRES` 可能为 null（不可读时 UI 不显示剩余天数） |
| R2 | 「应用保留 %1$d 天；到期后立即禁止恢复，后台尽快物理删除」 | 副本占用与源文件相近的空间；**卸载应用会删除这些副本，卸载后不可恢复** |

6. **`settings_trash_retention`（回收站保留时间）只对 R2 条目生效**，UI 需注明。
7. **30 天拆成两个指标**（`docs/architecture/Organizing-Page-Function-Design.md` §8.7）：
   - **恢复资格严格**：`now >= expiresAt` 立即禁止恢复。
   - **物理删除尽快**：到期入清理队列，后台重试，应用每次启动/进前台再检查。**不承诺物理删除精确到秒。**
8. **物理清理在下次打开应用时执行**（D3-C2），**必须在 UI 与文档中明说**（D7）。
9. **不得仅通过隐藏视频列表条目或修改数据库标记来冒充文件已安全移入回收站。** 移入必须有真实的文件系统动作 + 副本完整性验证 + 空间预检。

## 3. 后果

### 3.1 正面

- 默认路径**零额外空间**，这是移动端唯一可接受的默认。
- 与 `docs/06:264` 的「优先使用 MediaStore 系统回收站」一致，不需要修改路线图。
- R3 的删除同时修掉「对 `content://` 直接失败」与「原 URI 失效需重扫」两个问题。
- R2 的保留期可配（`settings_trash_retention`），保住了用户可配保留期这个产品能力——**D2-c（全量 R1）会丢掉它**。

### 3.2 负面 / 代价

- **两套期限语义**会增加 UI 分支与文案复杂度；用户可能困惑「为什么这个显示 30 天、那个显示我设的 7 天」。
- **R1 的 30 天不可保证**：产品不能承诺「严格 30 天」。
- **R2 的副本随卸载删除**，卸载即丢——必须在 UI 明说，否则是隐性数据损失。
- 需要 `trash_entries` 增加 `backend` 字段（`R1` / `R2`）。
- 需要 P0-B 验证才能启用 R2 路径；未验证前 R2 只能返回 R4。

### 3.3 中立

- `trash_entries` 主键从 `mediaItemId` 改为 `locationId`（修 G16），所有 11 处 `LEFT JOIN` 同步改。

## 4. 备选方案与否决理由

| 方案 | 否决理由 |
| --- | --- |
| **D2-b：全量 R2**（严格 30 天） | 空间 2×（移入峰值），在移动端不可接受；且卸载即丢，与「严格」的初衷矛盾 |
| **D2-c：全量 R1** | 放弃严格 30 天**且**放弃用户可配保留期；需删除 `settings_trash_retention`；SAF 树来源完全无法回收（只能 R4） |
| **保留 R3** | 对 `content://` 不成立（应用无路径访问权）；成功时也让原 URI 失效；文件既不受系统保护也不受应用期限管理。**正确性缺陷，必须删除。** |
| 引入 `MANAGE_EXTERNAL_STORAGE` | 不是合理默认方案；Google Play 对「所有文件访问」有专门限制 |
| 依赖 `JobInfo.Builder.setClipData()` 持久化一批 URI 的写权限 | **不能与持久化任务同时使用**，故不能把一批 URI 与写权限交给跨重启任务后就认为 30 天后仍可用 |

## 5. 验证方式

### 5.1 P0-B 最小验证（启用任何后端之前必须完成）

1. 对一个**本应用创建**的 `Movies/YingLi-Output` 视频与一个**其他应用创建**的视频，分别验证 R1 的移入 / 恢复 / 永久删除路径，以及 `DATE_EXPIRES` 是否可读、值是多少。
2. 验证在 **API 31 与 API 36** 上的行为差异（`minSdk = 31`，需两端都测）。
3. 验证 SAF 树来源的文件在 R1 下会发生什么（预期：不可用 → R4 或 R2）。
4. 验证「用户拒绝授权」后源文件仍完整、且回收站条目**不显示为成功**。
5. 空间不足 / 复制中断 / 进程被杀时**不得丢源文件**。
6. 恢复路径：先建后验再清副本。
7. `expiresAt` 边界行为。
8. 到期清理在重启与后台延迟后仍重试。
9. 卸载后行为：无孤立隐藏文件（针对 R2）。

### 5.2 契约与单元测试

1. 移入事务的每一步失败都必须**退回上一个稳定态**（6 态状态机：正常媒体 / 移入处理中 / 回收站中 / 恢复处理中 / 永久删除处理中 / 已删除）。
2. **不得把「复制成功」直接等同于「移入成功」**。
3. R1 条目 UI 文案必须包含「由系统管理」；R2 条目必须包含用户设定天数与卸载提示。
4. `settings_trash_retention` 只影响 R2 条目。
5. R3 代码路径必须**不存在**（删除后加断言）。
