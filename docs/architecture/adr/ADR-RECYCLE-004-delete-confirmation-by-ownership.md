# ADR-RECYCLE-004：永久删除按「文件所有权」分派确认方式

- **状态**：已采纳（Accepted）

- **取代**：无

## 1. 背景

### 1.1 第一性原理

「永久删除」在不同的存储位置上，**系统能提供什么保障是不同的**。由此推出：**确认方式必须按文件所有权分派**，不能用一套流程套所有对象。

| 对象 | 系统提供什么 | 应用能做什么 |
| --- | --- | --- |
| **共享媒体库中的文件**（MediaStore 管理的 `content://`） | `MediaStore.createDeleteRequest()` / `createTrashRequest()` / `createWriteRequest()`，需用户批准 | 发起系统授权请求；**不能**直接删他应用创建的媒体 |
| **应用私有目录中的文件**（`filesDir/recycle-bin/items/<uuid>`） | 无系统授权机制 | 自己的确认界面 + `File.delete()` |

关键事实：
- `MediaStore.createDeleteRequest()` **只适用于系统管理的共享媒体 URI**；**应用私有目录文件不能套用该系统确认**。
- 反过来，对应用私有目录中的普通文件**没有**系统授权弹窗可用——**不能虚称已调用系统媒体删除授权**。
- 批量授权请求**单次 URI 上限 2000**（目标 SDK 36）。
- Android 12（API 31）起 `MANAGE_MEDIA` 特殊访问权限可免逐次确认执行媒体修改，**但不自动赋予读取权限**，需用户在系统设置明确授予。

### 1.2 现状缺陷

`AndroidFileOperationGateway.purge()` 当前对 `content://` 直接 `resolver.delete(uri)`（G15）。这会抛 `RecoverableSecurityException` 而未被捕获处理，导致用户看到「删除失败」而不是「需要授权」。

---

## 2. 决策

**永久删除的确认方式按对象所有权分派：**

| 对象 | 确认方式 | 理由 |
| --- | --- | --- |
| **R1 条目**（仍在共享媒体库中，`IS_TRASHED = 1`） | 应用确认 → 若源非本应用创建，走 `MediaStore.createDeleteRequest()` 等系统授权 | 系统媒体删除授权只适用于共享媒体 URI |
| **R2 条目**（应用专属目录中的副本） | **应用自己的确认界面**，然后 `File.delete()` | 应用私有目录中的普通文件**不能**套用 `createDeleteRequest()`；**不能虚称已调用系统媒体删除授权** |
| **批量 / 清空** | 先展示条目数量、不可恢复警告与失败可能性，应用确认后逐项执行、逐项记录 | 参考资料文件 8 §8.5 |

### 2.1 必须遵守的规则

1. **支持部分成功。删除失败的条目保留记录并进入 `CLEANUP_PENDING`。**
2. **「清空」不能先清数据库再删文件**：每个文件确认删除成功后才删除相应元数据。
3. **不能静默把授权拒绝或 I/O 失败变成永久删除。**
4. **永久删除不得通过隐式失败回退触发。**
5. **批量授权请求单次 URI 上限 2000**（目标 SDK 36），必须分块并逐块记录用户授权结果。
6. **删除前必须确认目标文件仍对应该回收站条目**：
   - R2：用 `copyRelativePath` 的 UUID + 记录的 `copySizeBytes` / `contentHash` 校验；
   - R1：用 `locationId` + `originalUri` + MediaStore `_ID` 校验。
   **目的是避免误删路径被覆盖后出现的新文件。**
7. **物理删除成功后再删除数据库记录；失败则保留条目（`CLEANUP_PENDING`）、错误详情和重试信息。**
8. **修 G15**：`AndroidFileOperationGateway.purge()` 必须改为：捕获 `RecoverableSecurityException` → 返回 `RecoverableFailure(PERMISSION_REQUIRED)` 并携带可发起 `createDeleteRequest()` 的 URI 集合 → 由上层发起系统授权 → 用户确认后重试。

---

## 3. 后果

### 3.1 正面

- **不虚称授权**：R2 条目走应用自己的确认，不假装调用过系统媒体删除授权。
- **不误删**：删除前的位置校验挡住了「路径被覆盖后出现的新文件」这一类真实风险。
- **可恢复的中断**：部分成功 + `CLEANUP_PENDING` 使批量删除在失败后可以续做，而不是整体回滚或整体放弃。
- 与「成功状态只能由独立验证产生」的项目原则一致：**删除成功必须由文件系统事实确认，而不是由 API 调用未抛异常推断。**

### 3.2 负面 / 代价

- 两条确认路径意味着 UI 有分支：R1 可能弹出系统对话框，R2 只弹应用自己的对话框。用户可能困惑「为什么这次弹系统框、那次不弹」。**必须有文案解释。**
- 2000 上限要求分块逻辑，且要逐块记录授权结果（部分块被拒时的语义必须定义）。
- 批量删除的「部分成功」状态需要在 UI 上有明确的呈现方式（成功 N 项 / 失败 M 项 / 待重试 K 项）。

### 3.3 中立

- 参考资料文件 8 §1.1 的原文警告（「如果产品要求『回收站内每个私有副本的单项删除必须出现 Android 系统媒体授权弹窗』，则与应用专属副本存储方案不兼容」）在此决策下**被规避**：R2 条目本来就不要求系统弹窗。

## 4. 备选方案与否决理由

| 方案 | 否决理由 |
| --- | --- |
| 全部走 `createDeleteRequest()` | 对应用私有目录文件**不适用**（F29）；会失败或虚称授权 |
| 全部走应用自己的确认 + `File.delete()` | 对共享媒体库中他应用创建的文件**没有权限**，会抛 `RecoverableSecurityException` |
| 先删数据库记录再删文件 | 「清空」场景下会导致文件仍在但记录已消失（不可恢复的孤儿文件） |
| 删除失败时自动重试为永久删除 | 违反规则 3/4；把授权拒绝变成永久删除 |
| 用 `MANAGE_EXTERNAL_STORAGE` 绕过授权 | 不是合理默认方案；Google Play 对「所有文件访问」有专门限制 |
| 不做删除前位置校验 | 会误删「路径被覆盖后出现的新文件」（参考资料文件 8 §8.6 明确点名） |

---

## 5. 验证方式

1. **R1 路径测试**：本应用创建的媒体直接置 `IS_TRASHED`；他应用创建的媒体必须走 `createTrashRequest` / `createDeleteRequest`。
2. **R2 路径测试**：应用私有副本的删除**不得**调用任何 MediaStore 删除 API（断言调用次数为 0）。
3. **`RecoverableSecurityException` 测试**：注入该异常，断言返回 `RecoverableFailure(PERMISSION_REQUIRED)` 且携带正确的 URI 集合，而不是直接失败。
4. **用户拒绝授权测试**：源文件必须仍完整；条目**不得**显示为成功。
5. **2000 上限测试**：超过 2000 个 URI 必须分块，且逐块记录授权结果。
6. **删除前校验测试**：替换目标文件（同路径不同内容）后，删除必须被拒绝。
7. **部分成功测试**：注入单点失败，断言失败项进入 `CLEANUP_PENDING` 且携带错误详情与重试信息；成功项记录已删除。
8. **顺序测试**：断言「物理删除成功」严格早于「数据库记录删除」。
