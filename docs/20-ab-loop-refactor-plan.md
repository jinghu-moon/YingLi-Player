### 1.1 P0 阻断项已消解：D8 与"单一裁剪循环"的冲突 —— 裁决为采用 D8-A + 方案 A

单个 `ClippingMediaSource(A, B)` 只提供 `[A, B]` 区间，**无法播放 A 之前的内容**；这与 D8 的"A 之前继续正常播放"以及"循环期间允许拖到区间外"**在能力上冲突**，且该冲突**与位置语义是绝对值还是片段相对值无关**（无论 U1 观察到哪种，冲突都存在）。

**阶段 0 裁决（本轮）**：该 P0 阻断项**已消解**，路径不是"让裁剪源支持区间外"，而是：**采用 D8-A + 方案 A**（未裁剪源 + 手动精确回跳），从根上绕开"单一裁剪源没有区间外能力"这一能力缺失。证据见 `docs/19`：

- 裁剪源在区间外**不是"钳到 A"而是直接 `ENDED`**：`seekTo(12000)` 落点 `2010`、`advancedMsIn2s=0`、`playerState=ENDED`（`docs/19` "T0.1-U7/U8/U9"）；
- 切源换来的是**静止末帧 + 104 ms 帧空洞 + 3/3 次重缓冲**（`docs/19` "T0.1-U10"），即"区间外能力"并未真正买回来。

| 方案 | 含义 | 结论 |
|---|---|---|
| **D8-A + 采用方案 A**（**本轮裁决，正式采用**） | 保留 D8 语义：A 之前正常播放、抵达 A 后开始循环、循环期间可拖到区间外；循环由**手动 `seek(A)` + 强制 `EXACT`** 实现 | **采用**。方案 A 在未裁剪源上工作，**不需要切源**，因此 D8 冲突自动消失；实测落点 50/50 = 0 µs 帧精确、50 次无漂移（`docs/19` T0.2） |
| **D8-B：保留单一裁剪循环**（**不再采用**） | 修改 D8：激活后只能在 `[A, B]` 内播放与 seek | **不采用**：收窄产品语义，且仍解决不了坐标系/`ENDED` 问题（`docs/19` 取舍选项 2） |

**Q7 已定且本轮维持：采用 D8-A** —— 保留"A 之前正常播放、抵达 A 后开始循环"的既定体验；**不为了让单一裁剪源更简单而改成 D8-B**。

**本轮裁决确定的验收口径（替代 v3 的"两者对照"）**：

1. **方案 A 采用，但不等于整体验收完成**：方案 A 的循环点在实测中**每次出现一次 `STATE_BUFFERING`（27–45 ms，均值 37.3 ms，50/50 次）与 1 帧画面空洞**（`docs/19` T0.2）。因此 §3.4 的阈值按实测修订（不再要求"重缓冲计数 = 0"），且**音频连续性仍是未验证项**（阶段 2 阻断项，见 §3.4、§5 阶段 2、§6）。
2. **"无缝"一词从本文档的实现口径、UI 状态、测试名称与验收文案中删除**：产品名称统一为**「帧精确、低延迟循环」**；用户可见口径为：

   > **「循环点可能出现一次短于一帧的解码抖动；这不是严格无缝循环。」**

3. **若产品坚持绝对无缝**：进入 §1.2 的"双 `ExoPlayer` 预热"候选评估（附带代价），**不得**在未评估的情况下把"无缝"写回验收文案。

### 1.2 已排除方案（阶段 0 裁决）

本节记录**不再作为主线候选**的实现路线及其排除依据。证据全部来自 `docs/19` 的两个阶段 0 章节（真机 spike，Media3 1.10.1，设备 `f3ba305a`，素材 720×480 25fps，A = 20 000 ms / B = 22 000 ms）。

| 方案 | 形态 | 排除依据（要点） | 证据位置 |
|---|---|---|---|
| **方案 B：切源（未裁剪源 ⇄ 裁剪循环源）** | 进入区间前用未裁剪源，抵达 A 时切到 `ClippingMediaSource(A,B)` 循环源，离开时切回 | **四条都是结构性问题**：① 单一裁剪源**没有区间外能力** —— seek 到 A 之前不是钳到 A 而是直接 `ENDED`；② **坐标系不统一** —— 位置/seek 用窗口坐标，`Window`/`Period` 元数据用媒体时间坐标；③ 切源瞬间 **104 ms 帧空洞**（名义帧间隔 40 ms 的 2.6 倍）+ **3/3 次重缓冲**（36/60/116 ms）；④ 切进去即 `ENDED`，换来源只是一个**静止末帧** | `docs/19` "T0.1-U7 / U8 / U9"、"T0.1-U10" |
| **方案 C：拼接源** | `ConcatenatingMediaSource(ClippingMediaSource(base,0,A), LoopingMediaSource(ClippingMediaSource(base,A,B), N))` | ① **无限循环次数（`Integer.MAX_VALUE`）直接 ANR** —— 主线程卡在 `Timeline.equals → getNextWindowIndex`（`InfinitelyLoopingWindowCount=178956970`，`equals` 复杂度 ∝ 窗口数）；② **有限次数（10 000）同样失败** —— 每次回绕 **232–260 ms（5.8–6.5 帧，P95 257 ms）** 的画面空洞，且**素材尾部约 1.84 s 永远播不到**；③ `player.duration` 变成**当前 window 时长**（20 000 → 2 000）；④ 一切 ≥ A 的 seek 目标被钳回 `w0` 末尾（19 999），**拖不进循环段** | `docs/19` "方案 C（拼接媒体源）的验证"结论一/二/四/五 |
| **方案 C 的改进变体**（有限大循环次数 + 接近末尾追加、`setEnableClippingInMediaPeriod(true)` + `ClippingConfiguration` 组合） | — | **不作为主线**：前者只能把 ANR 换成"可用的有限时间轴"，**帧空洞与丢尾巴不会因此消失**；后者**未与循环组合验证**，且它要解决的是"裁剪"而不是"循环原语缺失" | `docs/19` 方案 C"未能覆盖/风险"第 5 条 |
| **`LoopingMediaSource(未裁剪源)`** | 只用 `LoopingMediaSource` 包住未裁剪源 | **逻辑上不满足 A-B 区间语义，无需单独 spike**：它只能循环**整个媒体**（0 → 媒体末尾），无法表达 `[A, B]` 区间，因此与 D5（A/B 毫秒口径）和 §3.1 的循环语义**直接矛盾**。这是**逻辑不满足**，不是"待验证项" | 判定为逻辑不满足；"单个 `LoopingMediaSource` 的回绕空洞"这一对照是方案 C 的遗留验证项（`docs/19` 方案 C"未能覆盖/风险"第 6 条），**与是否采用无关** |

**API 事实（Media3 1.10.1，`javap` 核对）**：`ConcatenatingMediaSource`、`LoopingMediaSource`、`ClippingMediaSource` **均已 `@Deprecated`**；替代品 `ConcatenatingMediaSource2` **没有循环原语**；**未弃用的裁剪路径**是 `DefaultMediaSourceFactory.setEnableClippingInMediaPeriod(true)` + `MediaItem.ClippingConfiguration`（**未与循环组合验证**，`docs/19` 方案 C "需要记录的 API 事实"）。→ 采用方案 A 也**顺带避开了在已弃用 API 上继续构建**这一长期成本。

### 2.2 ⚠️ 修正：AB 状态**不是单一权威源**（审核 P1；v3 补第三份）

原文档称"服务层已接 reducer、seek 会经过 limiter"，**高估了活跃链路的接线**。实际是：

- **播放页实际使用 `PlayerViewModel` 自己持有的一份 AB 状态**，并在本地调用 `AbLoopLimiter`（`feature/player/PlayerViewModel.kt:528` 一带）；
- 同时 `PlaybackSessionRuntime` 里**另有一份** AB 状态与 reducer（`app/playback/PlaybackSessionRuntime.kt:249` 一带）；
- **v3 补充（本轮核对）**：`PlaybackSessionClientBridge` 内**还有第三份** AB 状态（`app/playback/PlaybackSessionClientBridge.kt:42`），且它在每次 `publish` 时把自己的那份写回快照（`PlaybackSessionClientBridge.kt:226-241`，`abLoop = abLoop`）→ 会**覆盖**会话侧的取值。

→ 运行中的 UI 路径、会话路径、客户端桥接路径**并非同一个权威状态源**。

### 2.3 ⚠️ 修正：建源/引擎接口边界（审核 P1；v4 按方案 A 重述）

- `PlaybackEngine.prepare` 接收的是**不透明 source handle + 起始位置**（`domain/playback/PlaybackSessionContracts.kt:418` 一带：`suspend fun prepare(source: PlaybackSourceHandle, startPositionMillis: Long)`），**没有**任何表达"AB 区间"的入口；

## 3. 目标行为规格（v2；v3 按 Q7–Q10 更新 §3.1/§3.2 并新增 §3.4；v4 写死 generation/origin 语义并按阶段 0 实测修订 §3.4）

### 3.1 循环语义

- **设 A**：以当前位置为 A；若该位置 **> B** → A/B 互换；若 **== B** → **拒绝/无操作**（不互换、不改状态，避免产生 `A == B` 违反不变量）；
- **设 B**：位置必须 **> A**，否则拒绝并给 `INVALID_AB_RANGE`；
- **帧吸附**（D5，审核修正）：**按帧索引计算**，避免非整数帧率的取整误差：
  `frameIndex = round(ms * fps / 1000)` → `snappedMs = round(frameIndex * 1000 / fps)`；
  - 无可用帧率（实测与容器都为 0/缺失）→ 原样返回毫秒；
  - 吸附后**若导致 A == B**（或 < 一帧间隔）→ 按相等边界规则拒绝/无操作；
  - 注释与文档声明：这是**名义帧率吸附**，VFR 素材不承诺命中真实帧边界（D13）；
- **激活**：A、B 都设置后立即生效；
- **区间外行为**：按 **D8-A（阶段 0 已裁决保留，§1.1）**——**A 之前正常播放、抵达 A 后开始循环、循环期间可拖到区间外**；采用方案 A（未裁剪源 + 手动精确回跳）后该语义**无需切源即可成立**（§1.2 已排除方案 B/C）；循环点的抖动按 §3.4 修订后的阈值判定，**不承诺严格无缝**；
- **清除**：取消循环、清零计数；关闭胶囊**不**清除（D3）；
- **切歌/换媒体**：自动清除（`MediaChanged` 语义保持）；
- **循环计数**（D9）：必须来自**可区分的循环事件**，不得用"位置跨越 A"猜测（审核 P1，见 U2、§4.4）；
- **generation / origin 语义（v4 写死，唯一权威定义；§4.4 契约与 T1.1 引用本节）**：
  - 每次进入"新的循环有效配置"都要**生成新的 `loopGeneration`**：**A/B 变更**（含设点、互换、吸附后重设）、**清除**、**切媒体**（`MediaChanged`）**都会生成新的 `loopGeneration`**；
  - **用户 seek / 拖动 / 逐帧 / 队列切换** → **必须取消或重置旧边界消息**（旧 generation 的边界消息一律作废，不得再触发回跳）；
  - **只有当前 generation 的自然边界事件**（引擎上报的"播放自然抵达 B"）**才能增加循环计数**；
  - `SeekOrigin.AB_LOOP` **只用于引擎内部回跳**（`PlaybackSessionContracts.kt:253` 已存在该取值），**不得**由 UI/客户端用它表达用户跳转；用户发起的跳转一律带 `USER` / `DRAG_END` / `FRAME_STEP`；
  - **过期事件、用户 seek 造成的越界、重建/重缓冲造成的位置回退，都不得计数**；
  - **动机**：否则"把边界判定从 ViewModel 搬到 runtime/engine"只是**把位置猜测换了个地方**（`docs/19` 方案 C 已证明"位置回退/事件含糊"正是计数不可靠的根因）；没有 generation，晚到的旧事件会污染新配置的计数；
- **AB 启用策略**（Q10 已定，v3 修正判定时机）：
  - **未知时长 或 不可 seek → 禁用**（循环区间不可定义）；
  - **非本地 / 受保护（保险库）媒体 → 按实际能力决定**（底层真能 seek 就可用，不因"来源类型"一律禁用）；
  - **判定时机是播放器准备完成之后**，按**真实 timeline 的 `duration` 与 seekability** 判定，**不是**按来源类型或最初 metadata 一律禁用 —— Vault 打开时传入的 source handle 时长可能是未知值（`app/playback/PlaybackSessionRuntime.kt:272` 一带把 `source.durationMillis` 写进 `mediaInfo`、而 timeline 是空的），准备完成后真实时长由引擎 timeline 提供（`app/playback/ServicePlaybackEngine.kt:308-312`：`durationMillis = player.duration...`、`isSeekable = player.isCurrentMediaItemSeekable`）；
  - 并给出用户可见的反馈口径（禁用原因可读）。

### 3.4 循环质量与精度的量化验收（v3 新增；v4 按阶段 0 实测修订）

> 本节是循环点质量与落点精度的**唯一判定口径**，供 T2.8/T2.9/T2.10（阶段 2 落地验证）、T1.10/T1.11（阶段 1 单测口径）与 §6 风险表共同引用。
> **产品口径**：实现路线为**「帧精确、低延迟循环」**；**不宣称严格无缝** —— 用户可见说明为**「循环点可能出现一次短于一帧的解码抖动；这不是严格无缝循环」**。**主观感受不能单独作为通过依据。**

| 项 | 通过条件（阈值） | 判定方式 | 依据 |
|---|---|---|---|
| 循环落点误差 | 每次回到 A 的偏差 **≤ 1 帧**；名义帧率 `fps` 下即 **≤ `1000/fps` 毫秒**（25fps → ≤40ms，30fps → ≤33ms，60fps → ≤17ms） | 位置日志：每次回到 A 后立刻采样 `positionMillis`，与设定的 A 逐次求差 | 帧吸附（D5/D13）的最小可分辨单位就是 1 帧；≤1 帧等价于"落点与设定点落在同一帧内"。**方案 A 实测 50/50 = 0 µs**（`docs/19` T0.2） |
| 无累积漂移 | 连续 **50 次**循环内，**第 50 次偏差不得显著大于第 1 次**（同一量级，不允许随次数单调增大） | 同上的 50 次采样序列，首末对比 + 观察是否单调漂移 | 累积漂移是"循环点用相对量重算"这类实现错误的直接症状。**方案 A 实测全程恒 0** |
| 循环点重缓冲（**v4 修订**） | **每个循环最多一次 rebuffer**（不再是"计数 = 0"） | 循环点前后各 1 秒的 `STATE_BUFFERING` / `onIsLoadingChanged(true)` 日志计数与时长 | v3 的"计数 = 0"在真机上**做不到**：方案 A 实测 **50/50 次 `STATE_BUFFERING`，27–45 ms（均值 37.3 ms）**，且**短于一帧（40 ms）**（`docs/19` T0.2 口径说明）。**这是阈值过严的产品选择，不是测量误差** —— 故改为"每循环 ≤ 1 次" |
| 重缓冲时长 P95 | **P95 ≤ 名义一帧**（25fps → ≤40 ms） | 逐次时长序列取 P95 | 一帧以内的衔接视为不可感知；**方案 A 实测 27–45 ms，P95 落在 45 ms 量级**，与"≤1 帧"仅差毫秒级 |
| 重缓冲时长 max（**v4 修订**） | **逐次记录每次时长，并单独报告 max**；**max 不作为硬阻断，但必须定义测量容差：max ≤ 2 × 名义一帧**（25fps → ≤80 ms） | 逐次时长序列取 max，并连同 P95 一起写入证据 | **25fps 一帧 = 40 ms，而实测 max = 45 ms，二者不可同时成立** → 不能把"max ≤ 1 帧"写成硬门槛。**本轮明确采用"定义测量容差 + 不作硬阻断"**：容差取"再放宽一帧"，覆盖调度/时钟测量误差；一旦 max 超过 2 帧即视为回归，**P95 与 max 必须同时报告，不得只报 P95** |
| 音视频间断 | 逐帧录像中循环点**无丢帧**（不出现帧时间戳空洞，即**无超过 1 帧的空洞**）；音频**无静音段超过 1 帧** | 逐帧录像 + 帧时间戳序列核对；音频静音段按采样判定 | 与"≤1 帧"同一尺度。**注意**：方案 A 实测循环点**每次 1 帧空洞**（`frameGapCount=50`，`docs/19` T0.2），恰好卡在阈值上；**音频这一项至今无任何证据**（instrumentation 进程音频渲染器起不来，见下） |
| 音频连续性（**v4 新增，阶段 2 阻断项**） | **音频解码器确实启动**；循环点静音 ≤ 1 帧；**无重复/丢样本/明显 click**；播放速度、后台、锁屏下表现一致 | 必须在**能出声的宿主**（真实 app/service 进程或手工真机操作）上测量，逐项记录 | **方案 A 的音频连续性完全未验证**（`docs/19` T0.1 "未能覆盖" 1、方案 C "未能覆盖" 1）。**该项完成前不得宣称整体验收通过**（§5 阶段 2、§6） |
| 主观 | **无可感知卡顿** —— 必须与上面各项客观数据**同时满足**，不能只凭主观 | 真机回放 | 主观只能作为"客观达标后"的补充确认 |

**基线说明**：以上阈值是**当前测试设备（`f3ba305a`，Android 16）**上的基线；**换 ROM / 芯片 / 解码器 / 素材（含 VFR）后必须重测并重新记录基线**，不得直接套用。若实测达不到阈值 → 作为**产品取舍**上报（选项见 §1.1 第 3 点与 §6），**不得单方面降低本节阈值来"通过"验收**；阈值本身的修订必须像本轮一样附实测证据。

## 4. 架构设计（方案 A）与不确定点

### 4.1 媒体源包装已废弃（v4；方案 A 不重建媒体源）

**原形态（已废弃，仅作记录）**：AB 激活时 `LoopingMediaSource(ClippingMediaSource(builtSource, startUs = A, endUs = B), 无限)`。该形态属于**方案 B**，已由阶段 0 证据排除（§1.2）：区间外能力缺失、坐标系不统一、切源 104 ms 空洞与 `ENDED`；`LoopingMediaSource` / `ClippingMediaSource` 在 Media3 1.10.1 上还**均已 `@Deprecated`**。

**v4 决定**：**方案 A 不包装、不裁剪、不重建媒体源** —— 引擎在未裁剪源上执行精确回跳即可。由此：

- **建源路径不需要为 AB 改动**（`prepare` 仍只收不透明 handle + 起始位置；`VaultAwareDataSource` 等 factory 配置不受影响）；
- 原先"如何把区间送进建源 / 如何保留受保护源配置 / 重建后如何续接位置"三项**全部消失**；
- **A/B 边界更新（Q9）随之简化**：不再涉及"裁剪边界何时重建"，A/B 只是引擎的回跳目标 → **设点成功提交后立即生效**（不存在"待应用 vs 生效中"的批处理分支需求）。原"可变裁剪"选项（U11）**不再需要验证**（见 §4.3）；
- 唯一保留的接口缺口是**引擎事件/循环配置契约**（§2.3 已重述），修复方案见 **§4.4**。

### 4.4 引擎契约扩展（v4 新增；阶段 1 第一步，先于删 UI 轮询）

**为什么必须先做这一步**：**当前 `PlaybackEngine` 没有事件流** —— 它只暴露 `state` / `capabilities` 与命令式方法（`domain/playback/PlaybackSessionContracts.kt:418-429`，**无 `events`、无循环配置入口**）。因此**阶段 1 不能只删 ViewModel 的轮询代码**：删掉之后"到达 B"这件事**没有任何通道能被上报**，循环会直接失效。契约必须先扩出来。

**契约草案**（风格与 `docs/17` §"PlaybackEngine 与能力端口"一致：接口 + 能力端口，不暴露 Media3 类型）：

```kotlin
interface PlaybackEngine {
    val state: StateFlow<EngineState>
    val events: Flow<PlaybackEngineEvent>            // 新增：引擎事件流
    fun configureAbLoop(loop: EngineAbLoop?)         // 新增：循环配置（null = 关闭）
    // ... 其余方法保持现状：prepare / play / pause / stop / seekTo / bindSurface / unbindSurface / release
}

/** 循环配置：generation 由 runtime 生成并持有（§3.1），engine 只消费。 */
data class EngineAbLoop(
    val generation: Long,
    val pointAMillis: Long,
    val pointBMillis: Long,
)

sealed interface PlaybackEngineEvent {
    /** 播放自然抵达 B；只有当前 generation 的该事件才允许被 runtime 计入循环次数。 */
    data class AbBoundaryReached(val generation: Long, val positionMillis: Long) : PlaybackEngineEvent
}
```

**配套约束（写入契约时必须同时成立）**：

1. **回跳由引擎执行**：引擎在收到当前 generation 的边界事件后，**自行**执行"回跳到 A"（配置 `SeekParameters.EXACT`），**不依赖 UI 或 runtime 反复下发 seek**；该回跳在命令层面对应 `SeekOrigin.AB_LOOP`（`PlaybackSessionContracts.kt:253`），**只用于引擎内部回跳**（§3.1）；
2. **坐标系**：`EngineAbLoop` 的 A/B 与事件里的 `positionMillis` 一律是**引擎 timeline 的绝对媒体毫秒**（方案 A 不裁剪，二者一致；坐标系规则的精确表述见 §2.4）；
3. **业务规则不下沉**：设点校验、A/B 互换、相等边界、帧吸附、启用策略、计数递增条件**全部留在 runtime**（§2.2）；引擎只做"检测边界 + 回跳 + 上报"，**不得**在引擎里复制 `AbLoopState` 的不变量；
4. **取消/重置**：`configureAbLoop(newGeneration)` 与"用户 seek/拖动/逐帧/队列切换"都必须**取消或重置旧 generation 的边界消息**（§3.1）；引擎需要暴露或内部保证这一语义，使**过期事件不会被上报**；
5. **事件必须可区分**：`AbBoundaryReached` 只能由**自然播放**触发 —— 由用户 seek 越界、重缓冲位置回退、暂停期间的位置变化产生的"跨过 B"**不得**触发该事件。

**边界检测归属（明确写死）**：

- 由**引擎**负责，**优先评估 Media3 `PlayerMessage` 定点消息**（在 B 位置安排一次播放器消息；`app/src` 全量检索确认**当前代码库尚未使用** `createMessage` / `sendMessage` / `PlayerMessage`，属新增 API 采用与验证项 **U12**，在 T1.1 内评估）；
- 若 `PlayerMessage` 在**用户 seek、暂停、重缓冲**场景下不可靠 → 实现**引擎内部的主线程边界调度**（例如在引擎自己的主 Looper 上按位置采样推进，**仅在 AB 激活且正在播放时运行**），并配套取消/重置语义；
- **明令禁止**恢复成 **ViewModel ticker**（`PlayerViewModel.kt:1285-1302` 那种 UI 轮询）或任何 **UI 按位置猜测** 的实现；违反即视为回到本方案要修掉的那个根因。
